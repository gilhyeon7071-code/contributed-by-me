# 가상매매 초기 안정화 운용 기준

## 목적
- 가상매매 초기 단계에서는 수익률 확대보다 로직 안정성, 데이터 정합성, 차단 근거 재현성을 우선한다.
- 로직 검증 중에도 동일한 판단을 유지하기 위해 운용 모드, 리셋 기준, 최소 주문 허용 기준, 검증 종료 기준을 고정한다.

## 기본 판단
- 현재처럼 후보가 있어도 주문 가능 수량이 0이 되는 상태는 즉시 실패로 보지 않는다.
- 다만 주문, 체결, 원장, 손익 검증이 계속 멈추면 별도 세션으로 분리해 검증을 이어간다.
- 기존 원장과 로그는 삭제하지 않는다. 과거 차단, DDM, 원장 누락, 체결 불일치 기록은 감사 증거로 보존한다.

## 운용 모드

### 1. 감사 보존 모드
- 기존 원장, 체결, 주문, PnL, 상태 JSON을 유지한다.
- 기존 문제의 원인 추적과 재현성 확인에 사용한다.
- 임의 리셋, 임의 삭제, 상태값 하드코딩 보정은 금지한다.

### 2. 분리 재시작 모드
- 기존 원장을 지우지 않고 새 `paper_session_id` 또는 `run_id`를 부여해 새 가상매매 세션을 시작한다.
- 대시보드는 기본적으로 현재 세션을 표시하고, 이전 세션은 감사/비교용으로 보관한다.
- 세션 분리 기준은 아래 중 하나 이상이다.
  - 보유 종목이 없는데도 DDM 또는 risk-off 이력 때문에 신규 매수가 계속 0으로 고정된다.
  - 주문 가능 수량 0 상태가 반복되어 주문-체결-원장 검증이 불가능하다.
  - 원장/체결 정합성 문제의 원인 분석을 위해 과거 세션과 신규 검증 세션을 분리해야 한다.

### 3. 최소수량 검증 모드
- 수익률 제고 목적이 아니라 파이프라인 검증 목적으로만 사용한다.
- 허용 목적은 후보 -> 주문 -> 체결 -> 원장 -> PnL 반영 체인의 정상 작동 확인이다.
- 거시/뉴스/데이터 정합성/원장 누락 같은 필수 차단은 우회하지 않는다.
- 허용하더라도 주문 금액과 종목 수는 별도 정책에 명시된 최소 범위로 제한한다.

## 리셋 금지 기준
- 원장 리셋은 기본 금지한다.
- 다음 항목이 확인되지 않으면 리셋하지 않는다.
  - 리셋 대상 세션의 백업 완료
  - 리셋 사유가 정책 변경인지 버그 복구인지 구분
  - 리셋 후 비교할 이전 세션의 보존 경로
  - 리셋 후 새 세션 ID
  - 리셋 후 실행할 검증 명령과 확인할 산출물

## 검증 유지 기준
- 로직 검증 보고에서는 매번 아래 항목을 분리한다.
  - 정상 차단: 정책상 막힌 것이 맞는 경우
  - 과도 차단: 보유 종목/현금/수량 조건상 검증은 가능해야 하는데 막힌 경우
  - 데이터 차단: 파일 누락, 날짜 불일치, stale, 원장 누락 등 입력 품질 문제
  - 운용 차단: DDM, risk-off, kill-switch, exposure cap 등 계좌 상태 문제
- 신규 매수 0건은 반드시 위 분류 중 하나로 설명되어야 한다.
- "수량 0"만 표시하고 세부 근거가 없으면 검증 미완료로 본다.

## 완료 판정
- 안정화 검증 완료는 다음을 모두 만족할 때만 말한다.
  - 후보가 탈락한 경우 탈락 단계와 근거가 종목별로 남는다.
  - 주문이 생성된 경우 주문 ID, 체결 ID, 원장 ID가 연결된다.
  - 주문-체결-원장 누락 건수가 0이다.
  - 신규 매수 0건이면 `정상 차단/과도 차단/데이터 차단/운용 차단` 중 하나로 설명된다.
  - 공식 Python 기준 산출물이 최신으로 재생성되어 있다.

## 현재 결정
- 기존 원장은 보존한다.
- 필요 시 리셋이 아니라 분리 재시작을 우선한다.
- 초기 단계에서는 수익률보다 로직 안정성, 체인 정합성, 차단 근거 재현성을 우선한다.
- 다만 모든 매수가 막혀 체인 검증이 불가능하면 최소수량 검증 모드를 별도 정책으로 열 수 있다.
