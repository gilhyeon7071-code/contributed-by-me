# 목적 원장 (Objective Ledger)

**왜 있나.** 이 프로젝트의 목적함수는 여러 번 바뀌었는데 **이전 목적의 종료 선언이 없었다.**
그래서 옛 목적의 잣대와 장치가 코드에 그대로 살아 있고, 매일 판정을 내며,
새 목적의 작업과 섞인다. 2026-08-29 에 R6(노출률 기록)를 고친 것이 그 예다 —
그것은 "자동 승격" 시대의 선행조건인데 그 목적은 이미 닫혀 있었다.

**규칙.** 목적을 바꿀 때는 **이전 목적을 명시적으로 종료 선언**하고,
그 목적에 속한 살아 있는 장치를 어떻게 할지(끄기 / 참고로 격하 / 유지) 적는다.
적지 않으면 그 장치는 계속 현재 목적인 척한다.

순서지 정의가 아니고, 수익률이 무엇 대비인지 정해진 적이 없어 합격선이 두 개로 갈려 있었다

이 원장(목적)은 그 정의 **아래**에 있다. 목적을 새로 세울 때 정의와 맞는지 먼저 본다.
기존 코드는 계획이 요구할 때만 불려 나온다. 안 불리면 판단 대상도 아니다.

정의에서 나온 합격선 (2026-09-13 확정, 역산으로 맞춤):
```

신호 합격선   +1.17%p             **h20 기준으로 잴 것** (지금까지 h10 으로 쟀다)

```

### 왜 O5 를 닫는가

**O5 에는 종료 조건이 없었다.** 작업 규율은 있는데 "언제 끝나는가" 가 없다.
그래서 구조적으로 안 끝난다 - 스캔할 때마다 나오는 것을 전부 일로 만든다.

그리고 우선순위가 뒤집혔다. 원칙은 **①매매가능 → ②수익률 → ③오류수정** 인데
2026-09-12~13 이틀을 ③만 했다.

```
① 로 간 것   최소수량 바닥 수리(진입이 막혀 있었다)      1건
② 로 간 것   전진 선택 평가 첫 숫자                      1건
③ 오류수정   나머지                                     30건 넘게
```

**그 30건 중 매매를 실제로 막고 있던 것은 0건이다.**
전부 **보는 층**이었다 - 화면이 거짓말하고, 신선도 감시를 아무도 안 읽고,
원장에 평가자가 없었다. 매매가 고장난 게 아니라 **매매를 볼 눈이 없었다.**
그건 끝이 있다. 다 재고 나면 멈춘다.

### O6 의 종료 조건 — **이번엔 적는다**

```
끝났다고 말할 수 있는 조건
  신호 -> 후보 -> 진입판정 -> 주문 -> 발주 -> 체결 -> 원장 -> 통계 가
  **한 거래일에 끝까지 한 번 돈다.** 그 증거가 산출물에 남는다
  -> AGENTS.md 7절: 6축 전부 PASS + 런타임 증거
판정일   2026-09-14(월) 첫 시도. 실패하면 멈춘 지점이 한 곳으로 나온다
```
되든 안 되든 **그날 답이 나온다.** 지금처럼 서른 갈래가 아니라 한 지점이다.

### O6 에서 바뀌는 규칙

```
O5      결함을 찾으면 고친다 (한도 없음)  -> 그래서 안 끝났다
O6      **①을 막는 것만 고친다.** 나머지는 대장에 올리고 손대지 않는다
        판단 기준: 이것을 안 고치면 사슬이 한 번 못 도는가
```
대장(`OPEN_ITEMS_REGISTER.md`)의 카드 27건이 그 대기 목록이다.
`--cards` 가 비어 있는 항목을 매번 보여주므로 잊히지 않는다.

### O5 에 속한 장치 — 어떻게 할 것인가 (규칙상 명시 필요)

```
유지   야간 불변식 감시 6단계 (boundary/freeze/verify x3/observation)
       -> 자동이라 사람 시간을 안 먹는다. O6 의 검증 근거이기도 하다
유지   고장 구간 대장 / 처리 카드 / 미결 대장
       -> 기록 장치이지 작업이 아니다
중단   **스캔해서 결함을 찾는 행위.** O6 동안 하지 않는다
       결함은 ① 작업 중에 걸리는 것만 본다
```

### 정정 2026-08-31 — 이 절의 원래 문장이 틀렸다

원래 이렇게 적혀 있었다: *"이 장치들은 매일 돌며 판정을 낸다. 현재 목적이 UNDECIDED 라 처분 보류."*

**틀린 곳이 둘이다.**

(1) **처분을 목적 결정에 묶은 것.** 이 원장의 규칙은 "닫힌 목적의 장치에 **새 작업을 투입하지 마라**"
    이지 "끄지도 마라" 가 아니다. 규칙이 만들어진 계기(08-29 R6 노출률)가 정확히 *투입* 사례였다.
    그리고 문서가 이미 수리를 면제하고 있다:
      rd_authorization.json exempt  "운영 배관 수리", "측정 절차 자체의 결함 수리"
      기준서 v1.1 §1                "운영 배관 수리와 결함 진단은 대상이 아니다(측정이 아니라 수리다)"
    SUSPENDED 가 막는 것은 새 확증 라운드이지 수리가 아니다. **선언은 처분의 선행조건이 아니다.**

(2) **네 개를 한 덩어리로 본 것.** 위 (가)/(나) 대로 성격이 갈린다.
    "O1 장치니까 끈다" 로 갔으면 후보 생성을 껐을 것이다.

=> **처분을 막는 것은 선언이 아니라 생산 의존성이다.** 선언은 "다음에 무엇을 잴 것인가" 에만 필요하다.

=> 그리고 이 절이 드러내는 더 큰 사실: **O1 은 2026-07-27 에 종료 선언됐지만
   코드에서는 끝나지 않았다.** 생산의 매매 가부를 O1 의 게이트가 매일 판정하고,
   생산의 인자 정의가 O1 의 HPO 파일을 출처로 가리킨다.
   **선언이 코드를 바꾸지 않았다.** 종료 선언을 하나 더 쓰는 것으로는 다음 것도 안 바뀐다.
