## 0. 왜 있나

지금까지의 작업은 **개별 게이트의 문턱이 옳은가**를 물었다. 0.75 는 적정한가, open_chase 0.05 의
근거는 무엇인가, min_oos_pf 를 1.0 으로 올릴 것인가.

그런데 그보다 먼저 물어야 할 것이 있다 — **이 판정 양식이 이 로직에 적합한가.**
양식이 로직에 맞지 않으면 문턱을 어디에 두든 PASS 든 FAIL 든 똑같이 의미가 없다.

실례가 2026-08-31 에 나왔다. 게이트 입력을 현재 로직으로 재계산했더니 세 축이 전부 FAIL 로
뒤집혔는데(§7), **그 FAIL 자체가 창당 28~51거래로 계산된 PF 다.**
28거래로 얻은 PF 0.4476 을 "불합격" 이라고 말할 수 있는가. 말할 수 없다.
뒤집힌 결과도 뒤집히기 전 결과와 같은 양식 위에 있다.

**따라서 순서는 (1) 양식 판단 -> (2) 분류 -> (3) 문턱 조정 이다. 지금까지 (3)만 해 왔다.**

## 1. 현재 양식 (있는 그대로. 2026-08-31 실측)

`utils/stable_params_gate.py` + `paper/paper_engine_config.json::stable_params_quality_gate`

```
주지표     PF (총이익 / 총손실). 절대값. 벤치마크 없음
표본단위   거래 (n_trades 가중)
기간단위   1년 롤링 창 7개 (IS 3 / VAL 2 / OOS 2)
판정       문턱 통과 여부, 이진
           require_promoted / min_oos_trades 20 / min_oos_pf 1.0
           min_mean_pf 1.0 / min_oos_worst_fold_pf 0.75 / min_stable_score -20
출력       PASS / BLOCK / WARN  (3값)
입력 출처   **stable_params_v41_1.json 에 저장된 windows 배열**
           = 게이트는 현직을 재계산하지 않는다 (2026-08-20 부터 미해결로 기록됨)
```

규모: `paper_engine_config.json` leaf 1,033개 중 게이트성 키 541개
(숫자 임계 297 / 불리언 스위치 163) + `stable_params_v41_1.json` 숫자 파라미터 30개.
그런데 `log_gate_event` 로 **등록된 게이트는 5종**, 2026-08-31 에 실제로 이벤트를 남긴 것은 **2종**이다.

## 2. 로직의 성질과 어긋나는 지점

근거가 기록에 있는 것만 적는다.

### 2.1 검정력이 구조적으로 없다

```
이 전략의 진입일 일간 초과수익 sd = 10.87%, 축적 속도 연 126 진입일
  2.0%p/day 검출 1.8년 / 1.0%p 7.4년 / 0.5%p 29.5년      (.agent/PLANS.md 2026-08-24)
그런데 게이트의 판정 단위는 **1년 창**이고, 창당 거래는 28~51건이다
```
**문턱을 넘고 못 넘고의 대부분이 잡음이다.** 이것은 문턱 값의 문제가 아니라 단위의 문제다.

### 2.2 기준선 칸이 없다

PF 는 절대 지표다. 시장이 오르면 무엇을 사도 오른다.
2026-08-28 에 **"기준선은 실제 대안 + 스타일 일치 둘 다"** 가 원칙으로 확립됐고,
같은 포트를 기준선만 바꿔 재면 +3.017%p(t=+4.98) 부터 -7.571%p(t=-1.61) 까지 부호가 뒤집힌다.
**게이트에는 기준선을 적는 칸 자체가 없다.**

### 2.3 표본 단위가 겹친다

같은 날 여러 종목을 진입한다. 거래 단위 유의성은 p 를 과대평가한다(2026-08-24 기록).
`n_trades` 가중은 하루에 몰린 진입을 독립 표본으로 센다.

### 2.4 재는 세계가 생산과 다르다

```
optimizer  hold=10 / max_pos=20 / fee=0.00358   (DEFAULT_FROZEN 폴백. base 27키에 hold·max_pos 없음)
생산       hold=13 / max_pos=6
실제       보유 중앙값 1일, 당일왕복 30%
```
`stable_params_v41_1.json` 의 `hold=13` / `max_pos=6` 을 **옵티마이저는 한 번도 쓰지 않았다.**

## 3. 핵심 진단 — 하나의 양식으로 두 개의 결정을 내린다

```
승격 판정   "파라미터 A 가 B 보다 나은가"    필요한 증거: 상대 비교 + 검정력
가동 판정   "이걸 돌려도 되는가"            필요한 증거: 하방 한도 + 판정 불가 시 기본 동작
```

이 둘은 필요한 증거의 **종류**가 다르다. 2026-08-20 에 `certified` / `operational` 로
**라벨은 갈랐으나 양식은 갈리지 않았다.** 지금 둘 다 같은 PF 문턱을 쓴다.
그래서 "인증 불합격 + 그래도 가동" 이라는 실제 상태가 **수동 플래그로만** 표현된다
(`operational=true`, `meta.manual_edit`, 2026-08-20). 표현할 칸이 없어서다.

## 4. 필요한 양식의 요건

### R1. "판정 불가" 를 1급 값으로 가진다

현재 출력은 PASS / BLOCK / WARN 셋이다. **표본 부족을 표현할 칸이 없다.**
그래서 잡음이 PASS 나 FAIL 로 반올림된다. 이것이 가장 큰 결함이다.

```
추가       INSUFFICIENT_EVIDENCE
판정 규칙   MDE > MES 이면 결과값과 무관하게 이 값을 낸다 (기준서 §4.1 과 동일한 규칙)
필수 부기   그때 시스템이 무엇을 하는가의 **기본 동작을 미리 정해 둔다**
```
기본 동작은 이 명세가 정하지 않는다. **선택지만 적는다** — 사용자 결정 사항이다.
```
(a) 판정 불가 = 차단      가장 보수적. 표본이 없으면 안 돌린다
(b) 판정 불가 = 통과+경고  현상과 가장 가깝다. 단 게이트가 게이트가 아니게 된다
(c) 판정 불가 = 축소 가동  규모를 줄여 표본을 쌓는다. 목적이 "표본 축적" 일 때만 정합적
```

### R2. 효과크기 + 불확실성으로 낸다

`"PF 0.4476 < 0.75 이므로 FAIL"` 이 아니라
`"효과 X, CI [a,b], n=28, 겹침보정 후 유효표본 m, MDE=Y"`.
문턱 비교는 그 다음이다. **문턱은 결론이 아니라 마지막 한 줄이어야 한다.**

### R3. 기준선을 필수 필드로

무엇 대비인가를 적지 않은 판정은 무효로 한다.
기준선은 **실제 살 수 있는 것 + 스타일 일치** 둘 다 만족해야 한다(2026-08-28 원칙).

### R4. 표본 단위를 명시하고 겹침을 보정한다

거래 단위 금지. 비겹침 블록 또는 일(day) 단위. 클러스터 단위를 등록표에 적는다.

### R5. 두 결정을 분리한다

```
승격 양식   상대 비교. 주지표는 기준선 대비 알파. 검정력 필수(MDE <= MES)
           표본이 부족하면 승격하지 않는다 (INSUFFICIENT_EVIDENCE = 승격 보류)
가동 양식   하방 한도 중심. 주지표는 손실 한도·낙폭. 절대 PF 아님
           표본이 부족할 때의 기본 동작을 R1 에서 정한 값으로 따른다
```

## 5. 분류 틀 — 327개 임계값을 어디에 넣을 것인가

모든 판정 임계값은 아래 넷 중 하나에 속한다. **어디에도 안 들어가면 "미분류" 다.**

```
[선정/승격] 통계적 상대 비교로 정당화해야 한다.   요건 R2 R3 R4 + 검정력
        파라미터의 우열(승격)과 종목 선정 임계값(v_accel_lim 6.6 등)이 **같은 칸**이다.
        코드가 하는 일은 다르지만 정당화 방식이 같기 때문이다.
        [개정 2026-08-31] 처음에는 `[승격]` 이라고만 적어 선정 임계값이 들어가는지 불명확했다.
        전수 분류(490건)에서 이 종류가 277개로 최다였다
[가동]   돌릴지 말지를 가린다.                요건 R1 + 하방 한도. 검정력은 부차
[집행]   개별 주문의 실행 가부를 가린다.       (스프레드·호가·수량 등)
        제도적 사실이나 집행 제약에서 오는 값. 통계 판정 대상이 아니다
[관측]   아무것도 막지 않는다. 기록·경보용.    문턱의 근거가 약해도 해가 적다
[미분류] 위 넷 어디에도 근거를 댈 수 없다.     **이것이 곧 근거 없이 눌러앉은 임계값이다**
```

각 임계값에 대해 적어야 할 최소 항목:
```
| 키 | 위치 | 분류 | 무엇을 막는가 | 근거 기록 위치 | 마지막 검증 |
```
`근거 기록 위치` 가 비면 자동으로 [미분류] 다.

**예상**: 표본으로 세 번 뽑았을 때 세 번 다 근거가 0건이었다.
```
worst_fold 0.75    "No derivation for 0.75 exists anywhere in PLANS.md"  (2026-07-27)
open_chase 0.05    근거 탐색 0건 + 설정 잠금 계약 우회                     (2026-08-20)
뉴스 축 39개 도구   매매에 닿는 4개, 검정된 것 0개                         (2026-08-20)
```
전수 조사는 아직 하지 않았다. **이 명세의 다음 작업이 그것이다.**

## 7. 근거 자료 — 2026-08-31 재현 시험

**용도 주의: 이것은 성과 자료가 아니라 "검증이 이루어졌는가" 에 대한 자료다.**

동일 시뮬레이터 / 저장값과 동일한 창 경계 / 현재 파라미터로 게이트 입력을 재계산했다.

```
                저장 (as_of 2026-08-14)      재계산 (2026-08-31)
OOS 2025        n=30  pf=1.5438              n=28  pf=0.4476
OOS 2026        n=39  pf=1.4026              n=51  pf=0.8011
avg_pf          1.3312                       1.0056
n_folds         6                            4

같은 게이트에 입력만 교체
  저장값    ok=True   oos_pf 1.4640 / mean_pf 1.1224 / oos_worst 1.4026
  재계산값  ok=False  oos_pf 0.6758 / mean_pf 0.9044 / oos_worst 0.4476
            reason = oos_pf_low ; oos_worst_pf_low ; mean_pf_low
```

차이의 원인은 최소 셋이고 하나로 귀속시킬 수 없다:
(1) 파라미터 변경(2026-08-20 require_macd_golden 0.0 / rule_e 비활성)
(2) 코드 변경(OOS 홀드아웃 분리 도입 — 저장값 n_folds=6 은 분리 이전 산물)
(3) 데이터 갱신(2022 폴드 n=4 -> n=0).

**셋 다 같은 답을 준다 — 게이트가 매일 읽는 숫자는 오늘의 코드·파라미터·데이터로 재현되지 않는다.**

그리고 이 결과 자체가 §2.1 의 대상이다. **뒤집힌 값도 28~51거래 위에 있다.**
이 명세가 완성되면 위 표는 "FAIL" 이 아니라 "판정 불가" 로 다시 읽혀야 할 가능성이 높다.

재현물: scratchpad `recompute_gate.py` / `recompute_gate_pinned.py` /
`recompute_result.json` / `recompute_result_pinned.json`. 생산 파일 변경 0.
