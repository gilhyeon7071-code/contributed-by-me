작성 2026-09-01. 상태 **승인됨 (2026-09-01, 사용자)**. 1단계 하네스 가동 중.
**단, 실제 발주(`--apply`)는 별도 승인 지점이며 아직 0건이다.**

## 1. 유니버스 - 알파가 아니라 집행 제약으로 정의한다

유니버스 문턱의 근거는 **"수익이 좋아서" 가 아니라 "체결할 수 있어서" 여야 한다.**
현재 value_min 1,550억은 고장난 시뮬이 고른 값이고 h10 -1.445%p (HAC -4.36) 로
측정된 유일한 유해 부품이다. 대체 근거를 아래처럼 유도한다.

```
계좌            100,000,000원 (가상)
동시보유        max_pos = 6
1포지션         약 16,700,000원
참여율 상한     일 거래대금의 **1%** (체결 충격 억제. 집행 제약)
=> 거래대금 하한 = 16,700,000 / 0.01 = **16.7억원**
   안전계수 2배를 적용해 **일 거래대금 20억원 이상** 을 하한으로 둔다
```
**이 값은 알파 주장이 아니다.** 계좌 크기가 바뀌면 같은 식으로 다시 계산한다.

추가 제외 - 전부 제도적 사실 또는 계산 제약이다.
**구현 상태를 같이 적는다. 문서에만 있고 코드에 없는 항목이 있었다(2026-09-02 실측).**
```
상장 126거래일 미만        지표 이력 부재        [구현됨] listing_days
당일 상한가 / 하한가        지정가 체결 불가      [구현됨] |change| >= 29.5%
가격 <= 1,000원           호가단위 비중 과대     [구현됨] close > 1000
우선주 / 신형우선주        상품 성격            [구현됨] 코드 6자리 숫자 AND 끝자리 0
                                             실측 영향 547 -> 534 (2.4%)
관리종목 / 거래정지         제도                 [**미구현**] tradability_blocked 가
                                             패널에서 실효 0건이다
ETF / ETN / 스팩          상품 성격            [**미구현**] market 컬럼이 52% UNKNOWN
                                             이라 시장 구분으로 못 거른다
```
**미구현 2건은 현재 유동성 하한(20억)과 코드 규약이 간접적으로 막고 있을 뿐이다.**
발주(`--apply`) 전에는 1순위로 승격된다. 지금은 목록행이다.

## 2. 점수 - 1단계에서는 알파를 주장하지 않는다

**1단계의 점수는 순위를 만들기 위한 자리표시자이고, 예측 주장이 아니다.**
이걸 명시하지 않으면 1단계 결과가 신호 검증으로 오독된다.

### 세 갈래를 동시에 돌린다

```
ARM_RANDOM    매일 유니버스에서 무작위 N 개.        **상설 대조군**
ARM_LIQ       유동성(20일 평균 거래대금) 상위 N.    체결 난이도 하한 확인용
ARM_SCORE     선형 점수 상위 N.                    2단계에서 축을 갈아끼울 자리
```

`ARM_RANDOM` 을 **영구 대조군으로 상설한다.** 근거: 과거 기록에서 무작위 선택이 -0.385%
일 때 게이트 선택이 -2.653% 였다. **선정이 무작위보다 나쁜지를 매번 자동으로 보이게 한다.**
앞으로 어떤 신호도 유니버스가 아니라 `ARM_RANDOM` 을 이겨야 한다.

`ARM_SCORE` 의 1단계 점수는 **동일가중 z-합** 으로 고정한다 (튜닝 금지).
구성 팩터는 이미 계산되는 것만 쓰고, 가중치는 전부 1 이다.
```
z(rs) + z(v_accel) - z(stretch) - z(atr14_pct)
```
**부호는 v41.1 의 현재 전제를 그대로 옮긴 것이며, 이 전제가 옳다는 주장이 아니다.**
(기록상 stretch/atr 은 IC 가 음수이므로 이 부호는 오히려 반대일 수 있다.
1단계는 그것을 판정하지 않는다.)

## 3. N 과 진입 규칙

```
N = 20        측정용 후보 수. 매일 정확히 20개
진입          그중 상위 6개 (max_pos). 기존 집행 로직 그대로
보유          **hold 13거래일 경과분만 매도. 손절/트레일은 1단계에서 쓰지 않는다**
              hold 13 은 stable_params_v41_1.json 값 그대로다. 튜닝하지 않는다
리밸런싱      강제 회전 없음. 매도는 hold 경과로만 발생한다
              (A1 개정 2026-09-02. 문서 말미 개정 이력 참조)
```
N=20 의 근거는 (a) max_pos 6 을 항상 채울 수 있을 것 (b) 하루 성과가 1~2종목에
지배되지 않을 것. **N 은 결과를 보고 바꾸지 않는다.**

## 4. 합격 / 불합격 - 1단계

**측정 대상은 매매 가능성이다. 수익률이 아니다.**

```
합격 (전부 충족)
  A1  후보 생성일 비율        >= 99% 의 거래일에서 정확히 N 개
  A2  완화 사다리 호출         **0 건** (L1~L7 을 한 번도 안 쓴다)
  A3  max_pos 도달률          워밍업 20거래일 이후 >= 90% 의 날에 6포지션
  A4  발주 대비 체결률         >= 90%
  A5  슬리피지 실측 중앙값      <= 0.50% (왕복). 백테스트 가정 0.358% 의 1.4배 이내
  A6  ARM_RANDOM 도 동일하게 A1~A5 를 충족 (기구가 신호와 무관하게 작동함을 확인)

불합격 (하나라도)
  B1  공집합 날이 1회라도 발생
  B2  완화 사다리가 호출됨
  B3  체결률 < 70%  또는 슬리피지 중앙값 > 1.0%
  B4  ARM_RANDOM 은 되는데 ARM_SCORE 만 안 된다 -> 점수 계산 결함이다
```

**수익률은 기록만 하고 판정에 쓰지 않는다.** 1단계 보고서에 수익률로 합격/불합격을
쓰면 그 보고서는 무효다.

## 개정 이력

사전등록 문서는 **결과를 본 뒤에 고치면 사전등록이 아니다.** 그래서 개정은
언제 / 무엇을 / 왜 / **그 시점에 관측된 결과가 있었는지**를 같이 적는다.

### A1 — 2026-09-02, 보유·청산 규칙 명시 (사용자 승인)

```
전   보유  기존 hold / stop / trail 그대로. 집행 파라미터는 건드리지 않는다
후   보유  hold 13거래일 경과분만 매도. 손절/트레일은 1단계에서 쓰지 않는다
```

**사유**: 원문은 모호했고 구현(`tools/topn_build_orders.py`)은 `hold=13` 만 넣었다.
설계서와 구현이 어긋난 채로 두면 나중에 어느 쪽이 계약이었는지 판정이 안 된다.

**왜 구현 쪽으로 맞췄나**: 1단계의 질문은 **"매일 살 게 나오고 체결되는가"** 다.
손절이 들어가면 보유 회전이 불규칙해져 `A3(max_pos 도달률)` 이 선택 기구가 아니라
**손절 빈도를 재게 된다.** 손절·트레일은 청산 규칙 비교이므로 2단계 문제다.

**이 시점의 관측 상태 — 개정이 정당한 근거**
```
실제 발주(--apply)        **0건**
체결                     **0건**
A3/A4/A5                 산출값 전부 0 또는 n/a (risk_off 로 전 주문 차단됨)
설계구간 수익률           **보지 않았다.** ARM 별 수익 계산 코드 자체가 없다
```
**결과를 하나도 보지 않은 상태의 개정이다.** 사후 조정이 아니다.

**바꾸지 않은 것**: 유니버스 하한 20억 / N=20 / ARM 3갈래 / 홀드아웃 봉인 /
A1~A6 합격 기준 / 가격 규칙(0.5% 버퍼). 전부 원안 그대로다.

## [2026-09-11] 조건 변경 — **같은 계좌에서 v41.1 이 소액 발주를 시작한다**

### 왜 같은 계좌인가

계좌를 나눌 수 없다. KIS 상시모의투자는 ID 당 국내주식 계좌 1개이고
(리그 2026/09/07~12/07, 투자원금 1억) 추가 발급이 불가능하다.
ID 를 바꾸면 **모의투자 정보가 전부 초기화**되므로 이 라운드 자체가 사라진다.

### 간섭 범위 — 무엇이 섞이고 무엇이 안 섞이나

```

              -> v41.1 이 산 종목은 positions.csv 에 들어오지 않아 보유 6/6 계산에 영향 없음
```
