# 장애 진단 순서

**로직에서 원인을 찾으면 그럴듯한 오답이 잘 나온다.** 순서를 지킨다.

## 0. 이 조사가 매매를 막고 있나

지금 매매 경로가 도는지 먼저 본다. 안 도는 것을 모른 채 다른 걸 파면
급한 것과 급하지 않은 것이 뒤바뀐다. "근거 없음"은 시급함의 근거가 아니다.

## 1. 나이부터 — 로직을 읽기 전에

```
판정 산출물의 generated_at
그 판정이 **읽은** 파일의 mtime / ts
둘의 시차
```
이 저장소의 소비자들은 산출물을 읽으면서 나이를 검사하지 않는다.
그래서 **직전 세션의 값이 오늘 값으로 재생되는** 결함이 반복된다.

```
2026-08-21  지수 틱이 전날 종가 -> 가짜 CIRCUIT_BREAKER + 가짜 BOOST 동시 발생
2026-08-21  surge_lob 이 11시간 전 스냅샷 -> 전 행 NO_LOB -> 진입 전량 차단
            데이터는 있었고 판정이 13분 빨랐을 뿐이다
```
전 세션은 로직에서 찾다가 "51일 죽은 소스"라는 **틀린 근본원인**을 적었다.

## 2. 시각과 거래일은 잰다. 추정하지 않는다

```
휴장일   holidays.json 이 정본
예약작업 DaysOfWeek / NextRunTime 을 XML 로 뽑아 본다
콘솔 출력 오전/오후가 깨져 보이면 판정 근거로 쓰지 않는다 (cp949 에서 둘 다 4바이트)
```
2026-09-10 에 깨진 "오후 9:30" 을 "오전 9:30" 으로 읽고 하루 계획을 잘못 세웠다.

## 3. rc=124 / timeout 은 진단이 아니라 **진단의 부재**다

```
반복되는 timeout 기록 = "느리다" 가 아니라 "원인을 모른다"
조치: 타임아웃을 크게 올려 **끝까지 돌린다.** 그러면 진짜 예외가 나온다
```
2026-09-10: `indicator_factor_diagnostic` 이 7주간 산출물 0 이었는데 기록은 매일
`returncode=124` 한 줄뿐이었다. 1200초로 올리니 7분 뒤
`ValueError: cannot convert float NaN to bool` 이 나왔다.
**300초가 7분짜리 작업을 잘라 그 뒤의 크래시를 한 번도 보여주지 않았다.**

## 4. 경보가 없다고 정상이 아니다 — 경보의 배선을 본다

```
경보가 상류의 죽음에 **얹혀** 발동하고 있었나?  -> 상류를 고치면 영구 침묵한다
경보 조건이 "정상이면 항상 참"인 항으로 쓰였나? -> 그건 다른 것의 부작용이다
경보가 전달은 됐나?                             -> 전달 단절이 로직 실패로 오인된다
```
2026-09-03 `POINTER_STALE` 이 정확히 1번 경우였고, 수리가 큰 실패를 **조용한 stale**
로 바꿀 뻔했다. 2026-05~08 에는 알림 45건이 전부 미전송이었다 —
"몰랐다"의 상당 부분이 로직이 아니라 전달 단절이었다.
**수리 후 경보가 여전히 뜨는지 실측한다.**

## 5. 그다음에 로직

여기까지 와서야 코드를 읽는다. 그리고 [[cite-check]] 대로 코드+실효설정+실행흔적 3종을 본다.

## 6. 고쳐도 끝이 아니다

```
배선을 고친 것과 로직이 맞는 것은 다르다
"체결 발생" 을 "매매 작동" 으로 바꾸지 않는다
FAIL 깃발만 따라가면 표본이 배선으로만 채워진다
```
