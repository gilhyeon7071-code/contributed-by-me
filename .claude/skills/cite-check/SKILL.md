# 인용 전 대조

기록은 쓰인 시점의 사실이다. **지금도 사실인지는 별개다.**
2026-09-11 하루에 세 번 틀렸다 — 애프터마켓 손절 무감시(실은 손절 자체가 없었다),
강제 청산 코드 부재(실은 있고 켜져 있었다), 08:30 배치 성격(실은 진입 스텝을 품고 있었다).
셋 다 대조 없이 인용해서 생겼고, 셋 다 그 인용 위에 작업 방향을 세웠다.

## 언제 발동하나

- PLANS / `.claude/projects/*/memory/` / `docs/references/` 의 문장을 근거로 쓸 때
- "없다 / 있다 / 죽었다 / 끝났다 / 안 돈다" 를 말하려 할 때
- 이전 세션·이전 결론을 이어받아 다음 작업을 정할 때

조사(읽기)에는 승인이 필요 없다. 대조를 건너뛸 이유는 시간뿐인데, 오늘 그 절약이
방향 자체를 틀리게 했다.

## 3종 대조 — 셋 다 본다

```
1. 코드        그 로직이 파일에 있나. 파일:줄 로 적는다
2. 실효 설정값  load_config() 결과를 본다. 설정 파일 원본이 아니다
               (DEFAULT_CONFIG 병합 층이 있다)
3. 실행 흔적    산출물 mtime / *_latest.json / 로그. **최근에 실제로 돌았나**
```

하나만 보고 결론내지 않는다. 셋의 조합이 답을 바꾼다:

```
코드 있음 + 설정 켬 + 흔적 있음    작동한다
코드 있음 + 설정 켬 + 흔적 없음    배선이 끊겼다 (부재가 아니다)
코드 있음 + 설정 끔               꺼져 있다 (없는 게 아니다)
코드 없음                         그때 비로소 "없다"
```

2026-09-11 DDM 사례: 코드 있음 + enabled=True + 흔적 있음 인데 **대상 원장이 비어**
있었다. "없다"고 적힌 메모는 틀렸고, 실제 문제는 부재가 아니라 단절이었다.
고치는 방법이 정반대다 — 신설이 아니라 배선.

## 대조 결과 처리

```
기록이 맞다        그대로 인용한다. 확인했다고 한 줄 적는다
기록이 틀렸다      **기록을 고친다.** PLANS 에 정정 항목을 쓰고, 메모 파일도 같이 고친다
                  틀린 채로 두면 다음 사람이 같은 자리에서 또 넘어진다
재현이 안 된다     "틀렸다"가 아니라 "재현 불가"다. 둘을 구분해 적는다
```

## 하지 말 것

- 헤더·요약만 읽고 넘어가기. PLANS 는 본문을 grep 한다 (`grep -an`, `-n` 은 잘린다)
- 일치하는 기록 여러 개를 증거로 세기. 같은 계보면 그건 **하나의 주장**이다
- 다른 문서로 옮겨 적을 때 대조 생략. 옮기는 순간이 가장 많이 틀리는 자리다
- 산출물의 자기 기술(라벨·플래그·설명 문자열)을 믿기. 산식을 재현해 확인한다
  상수를 고쳐도 설명 문자열은 안 따라온다
